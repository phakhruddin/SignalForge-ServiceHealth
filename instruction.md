# SignalForge Service Health

Build the cloud infrastructure and observability system for **SignalForge**, a
small asynchronous job service. The supplied application accepts jobs through a
public API, processes them in a worker, and continuously checks the complete
customer journey. Your job is to deploy the images and make service health
measurable through cloud logs, metrics, alarms, dashboards, and service-level
signals. Do not modify or replace the supplied images.

Use Terraform or OpenTofu for **all scored cloud resources**. The cloud is the
AWS-compatible endpoint in `/workspace/config/config.json`; do not contact a
real AWS account. The workspace has Terraform, OpenTofu, AWS CLI, Python, jq,
curl and diagnostic tools, but no Docker CLI or socket. Image names, endpoint,
region, and credentials-independent resource prefix are read from
that JSON file at execution time. Do not copy values from a particular rollout
into your source. The source contract is under `/workspace/contracts/`:

- `runtime.md`: image commands, environment variables, API, telemetry emitted
  by the programs, and diagnostic fault controls.
- `infrastructure.md`: network, compute, storage and observability outcomes.
- `observability.md`: metric dimensions, dashboards, alarms, SLOs, log and span
  records, and notification requirements.
- `schemas/manifest.schema.json`: required deployment manifest.

The supplied images have separate jobs:

1. `api_image` accepts HTTP jobs and exposes liveness, readiness and job-read
   endpoints. Run at least two replicas as an ECS service behind a public ALB.
2. `worker_image` reads the SQS queue and records completed jobs in DynamoDB.
   Run it as an ECS service on private subnets.
3. `canary_image` repeatedly submits a job through the ALB, waits for its
   DynamoDB-backed result through the public API, and emits end-to-end health
   telemetry. Run it as another ECS service on private subnets.

This is an observability task. The queue and table make the service real, but
the monitoring system is the primary deliverable. A healthy ALB target is not
proof that accepted jobs complete. The cloud resources must distinguish API
availability, worker progress, customer-journey success, and telemetry loss.

Write the answer under `/workspace/submission/`:

```text
/workspace/submission/
├── deploy.sh
├── destroy.sh
├── manifest.json                 # generated by deploy.sh
└── infra/
    └── one or more *.tf files
```

`deploy.sh` must use local Terraform or OpenTofu state in `infra/`, create or
update the system, repair a managed monitoring resource deleted after an
earlier deploy, and exit only after the API is ready. It must generate a
manifest containing real IDs from its state and the live cloud. It may take at
most 720 seconds, produce at most 8 MiB of output, and write a manifest no
larger than 1 MiB. Running it again must preserve accepted jobs and avoid
unnecessary replacement of the result table.

`destroy.sh` must remove only resources owned by this deployment, leave the
pre-existing baseline untouched, and complete within 900 seconds and 8 MiB of
output. The verifier invokes both scripts from the same writable submission
directory. Absolute `/workspace/submission` references and script-relative
paths are both valid.

The verifier will use fresh requests and documented diagnostic modes to
produce normal, slow, failed, stalled-worker and recovered behavior. The
observability system must reveal each condition through the public contract,
not through a verifier-specific file or hidden test name. Every metric or alarm
that is required to respond to traffic must use real emitted data; decorative
resources or a hand-written manifest do not satisfy the task.
